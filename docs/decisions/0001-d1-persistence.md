# ADR 0001 — Cloudflare D1 as the Risen datastore

- Status: accepted
- Date: 2026-09-20
- Affects: hosting, persistence, data ownership

## Context

`PLATFORM-SPEC.md` section 4 leaves the persistence choice open between
Cloudflare D1 and Postgres/Supabase, and instructs us not to pick Supabase
merely for login.

The repository already leaned towards D1 before this session:

- `db/index.ts` binds Drizzle to `env.DB` as a D1 database
- `db/env.d.ts` declares `DB: D1Database`
- `drizzle.config.ts` targets the `sqlite` dialect
- `vite.config.ts` wires the Cloudflare plugin and a local D1 binding
- the app deploys as a Cloudflare Worker (`wrangler dev` in `npm start`)

However `.openai/hosting.json` had `"d1": null`, so no binding was ever
created. Every database call therefore failed. The consequence was not
theoretical: the public dugnad RSVP on `/` had never worked. `GET /api/rsvp`
returned 503 on every request and the page permanently displayed
"Availability temporarily unavailable".

## Decision

1. Cloudflare D1 is the datastore for Risen's core records.
2. `.openai/hosting.json` sets `"d1": "DB"`, so the binding is actually
   provisioned. This is what fixed the RSVP endpoint.
3. Migrations are generated by Drizzle into `drizzle/` and checked into source
   control, as `CLAUDE.md` requires.
4. Reads go through `lib/risen/repository.ts` and nothing else. When no binding
   exists it returns the seed dataset and says so, so a missing database
   degrades to a labelled preview instead of an error page.
5. `data/risen.ts` is the seed dataset only. It bootstraps an empty database and
   backs the fallback. It is not a parallel store, and no module may read it
   directly instead of going through the repository.

## Consequences

- Object storage for photos, PDFs, offers and plans is still unresolved.
  `.openai/hosting.json` keeps `"r2": null`; enabling R2 is a separate decision
  and needs its own ADR.
- SQLite semantics apply: no native JSON columns, so `activity_log.metadata`
  holds a JSON string, and money is stored as whole NOK in integer columns.
- Deadlines and eligibility claims still need `sourceUrl` and `verifiedAt`
  columns before the Funding module can store them; `CLAUDE.md` rule 8 forbids
  presenting them as current without those. Until then they stay as clearly
  labelled illustrative copy.

## Binding D1 on deploy — resolved the hard way

Setting `"d1": "DB"` alone broke the production deploy. `vite.config.ts` wrote
the placeholder `database_id` `00000000-0000-4000-8000-000000000000` into the
built `dist/server/wrangler.json`, and Cloudflare rejected the whole deploy:

```
D1 binding 'DB' references database '00000000-0000-4000-8000-000000000000'
which was not found. [code: 10181]
```

Miniflare accepts any database id and keys local state by it, so the
placeholder is fine for `npm run dev`. Cloudflare requires an id that exists in
the account. The placeholder must therefore never reach a built config.

`vite.config.ts` now emits the D1 binding only when it has a real id:

- `CLOUDFLARE_D1_DATABASE_ID` set (a Cloudflare build variable) → the binding
  is emitted with that id
- not set, `vite dev` → the placeholder, because local Miniflare is happy with it
- not set, `vite build` → **no binding**, plus a build warning

A deployed worker without the binding falls back to the seed dataset and says
so on screen, which is a visible, safe failure. A deploy that fails outright is
not.

### To turn D1 on in production

See `docs/D1-SETUP.md` for the step-by-step version. In short: create the
database, set `CLOUDFLARE_D1_DATABASE_ID` as a build variable, run
`npm run db:remote -- --database <name> --confirm`, redeploy.

Applying migrations is a deliberate manual step rather than part of the deploy
command. Running schema changes automatically on every deploy is a decision
worth making on purpose, not by default; revisit it once there is real data.

## Alternatives considered

- **Postgres/Supabase** — rejected for now. It would mean leaving the Cloudflare
  Worker runtime the public prototype already deploys to, and the spec warns
  against choosing it for login alone. Revisit if file volume, offline needs or
  the collaboration model outgrow D1.
- **Leaving `d1: null` and shipping schema only** — rejected. It would have left
  the RSVP endpoint broken and the schema inert, with no way to verify that any
  of it works.
